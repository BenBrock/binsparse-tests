# Canonical Dense HDF5 Fixtures

## Goals

The canonical fixture family removes Matrix Market from parser verification.
Each fixture stores the semantic matrix in a dense HDF5 file and pairs it with
one or more committed reference `.bsp.h5` files.

The roundtrip harness remains in place for legacy coverage, but the canonical
fixture family is the intended replacement.

## File Contract

Each canonical file is a single HDF5 file with two compressed root datasets:

- `matrix`
  - the fully expanded semantic matrix
  - symmetric, Hermitian, and skew-symmetric Matrix Market inputs are expanded
    before writing
  - the dtype is minimized only after duplicate coordinates and symmetry
    expansion are applied
- `pattern`
  - `uint8`
  - `1` means the semantic coordinate is present in the canonical matrix
  - `0` means the semantic coordinate is absent and `matrix` must therefore be
    interpreted as the zero fill value at that coordinate

The root group also carries string/integer attrs used by generators and parser
adapters:

- `canonical_format_version`
- `name`
- `source_field`
- `source_symmetry`
- `structure`
- `is_iso`
- `value_dtype`
- `pattern_dtype`
- `source_url`
- `source_archive_member`

`structure` stores the preferred Binsparse structure for committed reference
generation. For general matrices this is stored as `general`.

## Dtype Selection

The canonical `matrix` dataset uses the smallest exact dtype that preserves the
semantic values:

- `pattern`
  - `uint8`
- `integer`
  - smallest signed/unsigned integer dtype that can represent the semantic
    min/max values
- `real`
  - `float32` if every semantic value roundtrips exactly through `float32`
  - otherwise `float64`
- `complex`
  - `complex64` if both real and imaginary components roundtrip exactly through
    `float32`
  - otherwise `complex128`

This rule is intentionally exact. A real matrix only qualifies for `float32`
when no precision is lost relative to the parsed Matrix Market values.

## Semantics

- Duplicate Matrix Market coordinates are summed before the canonical dtype is
  chosen.
- `pattern` tracks semantic occupancy, not just the stored triangle from the
  Matrix Market source.
- Explicit zero values remain visible through `pattern`, even when
  `matrix[row, col] == 0`.
- Phase 1 equivalence is therefore defined as dense values plus dense pattern,
  not just dense values alone.

## Test Phases

### Phase 1

1. Read canonical dense HDF5.
2. Read a committed reference `.bsp.h5`.
3. Check that the parser's in-memory sparse object is equivalent to the
   canonical dense values and pattern.

This phase requires the parser-specific `check_canonical_equivalence` binary.

### Phase 2

1. Read canonical dense HDF5.
2. Convert it to a requested Binsparse format such as `CSR` or `CSC`.
3. Compare the generated `.bsp.h5` file to the canonical dense fixture.
4. Compare the generated `.bsp.h5` file to the committed reference file for
   that format.

This phase uses the optional parser-specific `canonical2bsp` binary.

## Initial Corpus

The current manifest is `config/canonical_matrices.json`.

Initial committed SuiteSparse coverage:

- `HB/bcspwr01`
  - pattern symmetric
- `Pajek/GD99_b`
  - integer symmetric
- `LPnetlib/lpi_itest2`
  - real general, exact `float32`
- `HB/gre_115`
  - real general, requires `float64`
- `HB/young1c`
  - complex general
- `Bai/dwg961a`
  - complex symmetric

The initial committed reference set is intentionally small:

- `CSR`
- `CSC`

Future expansion should add more formats and eventually tensor fixtures.

## Tooling

`tools/build_canonical_corpus.py` regenerates canonical fixtures and committed
reference files from the manifest. The generator uses a configured parser entry
for `canonical2bsp`, so the reference corpus can be regenerated by whichever
implementation currently provides the densest coverage.
